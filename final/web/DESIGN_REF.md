# UI 레퍼런스 — 스티치에 넣을 재료

지금 구현된 6개 페이지를 기준으로 골랐다. 새로 갈아엎는 게 아니라 **지금 구조 위에 얹는다.**

---

## 0. 우리 화면이 무슨 장르인가

한 줄로 정하면 이렇다.

> **정부 사업을 위한 코드 리뷰 화면.**

- 검토 대상이 하나 있고(사업 = PR)
- 자동 점검 결과가 목록으로 나오고(체크리스트 = checks)
- 항목마다 근거로 파고들 수 있고(원문 링크 = diff)
- **확정이 아니라 후보**이며 사람이 결재한다(리뷰어 승인)

장르를 이렇게 잡으면 레퍼런스가 정해진다. 대시보드가 아니라 **리뷰 화면**이다.
지표를 늘어놓는 게 아니라 **판단을 돕는다.**

---

## 1. 레퍼런스 여섯 — 무엇을 가져올지까지

### ① GitHub — Pull request의 Checks / Files changed

**왜 맞나**: 우리 체크리스트와 구조가 같다. 항목마다 통과·실패, 옆에 Details, 눌러서 근거.
「확정이 아니라 검토 결과」라는 성격도 같다.

**가져올 것**
- 맨 위 **요약 배너** 한 줄 — `Some checks were not successful` 자리에
  「손볼 것 4건 · 확인만 3건」
- 체크 항목 한 줄의 구조: `상태 아이콘 · 제목 · 한 줄 요약 · [Details]`
- **파일 안에 인라인으로 다는 코멘트** → 우리는 표 안 수치 옆에 근거 링크
- 실패 항목을 위로 올리고 통과는 접어 두는 정렬

**안 가져올 것**: 초록/빨강 원형 아이콘 남발. 우리는 색보다 **실선/점선**이 우선이다.

---

### ② Linear — 이슈 목록과 상세

**왜 맞나**: 조밀한데 시끄럽지 않다. 상태를 색이 아니라 **형태 + 한 단어**로 말한다.
우리 화면도 정보가 많은데 결론이 조용히 서야 한다.

**가져올 것**
- 무채색 바탕에 **강조색 하나**만. 우리는 파랑(`#1f5fd0`) 하나
- 12~13px 조밀 타이포에 행간 넉넉히 — 표가 답답하지 않게
- 좌측 좁은 내비, 선택된 항목만 진하게
- **빈 상태 문장이 짧고 다정하다** — 우리 「빈칸의 네 가지 뜻」과 잘 맞는다
- 키보드 힌트(`⌘K`)를 구석에 작게

**안 가져올 것**: 다크 테마. 공무원이 인쇄해서 결재에 붙일 수 있어야 한다.

---

### ③ Stripe Dashboard — 결제 상세

**왜 맞나**: 금액·상태·이력이 한 화면에 있고 **모든 값에 출처가 붙는다.**
우리 `/budget`이 정확히 이 화면이다.

**가져올 것**
- **정의형 목록** — 왼쪽 라벨 회색 좁게, 오른쪽 값 진하게 (우리가 이미 쓰는 `dl` 구조)
- 값 옆에 붙는 **작은 링크 뱃지** — 우리 `.src`가 이미 같은 물건
- 상태 pill의 절제된 크기 (11px, 얇은 테두리, 옅은 배경)
- 표에서 **숫자는 등폭**(`font-feature-settings: "tnum"`) — 이미 적용돼 있다
- 위험한 값만 색을 쓰고 나머지는 먹색

---

### ④ Sentry — 이슈 상세

**왜 맞나**: **「이게 무슨 뜻이고 → 뭘 해야 하나」를 맨 위에 놓는다.**
우리 체크리스트의 「지금 이렇다 → 하고 나면 이렇게 된다」와 같은 구조다.

**가져올 것**
- 상단 카드에 **영향 범위를 한 문장으로** — 우리는 「돈 0÷2」 같은 것
- 그 아래 근거 원문(스택트레이스) → 우리는 **원문 인용과 링크**
- `Suspect commit` 처럼 **원인을 지목하는 한 줄** →
  우리 「여기서만 비어 있습니다. 돈을 주는 사업은 로봇·반도체에 4건 있습니다」
- **왜 이렇게 판정했는지 접어 두는 패널** — 우리 「왜 이 기준이냐」

---

### ⑤ 토스 — 송금·내역 화면

**왜 맞나**: 한국어로 **쉬운 말을 쓰면서도 신뢰감**을 잃지 않는다.
우리가 「덮는다」를 버리고 「해주는 사업」으로 간 방향과 같다.

**가져올 것**
- **문장형 제목**을 크게. 명사 나열이 아니라 「맡으신 사업이 기업이 필요하다고 말한 것과
  맞는지 확인합니다」 — 이미 랜딩에 적용돼 있다
- 숫자를 과감히 크게, 부연을 확실히 작게 (대비를 크게)
- **한 화면에 주요 행동 하나**
- 여백을 아끼지 않음 — 조밀함은 표 안에서만

**안 가져올 것**: 둥근 모서리 과다, 그라데이션, 일러스트. 결재 문서 성격과 안 맞는다.

---

### ⑥ 한국 정부 디자인시스템(KRDS) — 표와 상태 표기

**왜 맞나**: 심사위원이 「공무원이 실제로 쓸 수 있겠다」고 느끼는 데 필요하다.

**가져올 것**
- 표 머리 처리와 괘선 굵기 — 얇게, 가로선만
- 상태 뱃지의 **어휘**(확인·검토 필요·미확인)
- 명도 대비 기준 (본문 4.5:1)

**안 가져올 것**: 색·아이콘·둥근 버튼. 그대로 쓰면 2010년대 관공서 화면이 된다.
**뼈대만 빌리고 살은 ①②③으로 채운다.**

## 2. 우리 페이지별로 어느 레퍼런스를 쓸지

| 페이지 | 주 레퍼런스 | 핵심 패턴 |
|---|---|---|
| `/` 시작 | 토스 | 문장형 큰 제목 · 사업 고르기 카드 그리드 |
| `/todo` 지금 할 일 | **GitHub Checks** | 요약 배너 + 체크 항목 행 + Details |
| `/budget` 예산 | **Stripe 결제 상세** | 정의형 목록 · 값 옆 근거 뱃지 · 대조 상태 막대 |
| `/links` 연계 | **Sentry 이슈** + GitHub | 「왜 이 기준이냐」 접힘 · 관계도 |
| `/needs` 필요한 것 | Sentry + Linear | 빈칸을 원인 지목으로 · 자료 넣기 |
| `/action` 조치 | GitHub PR 병합 화면 | 최종 확인 + 문서 내려받기 |

## 3. 반드시 지켜야 하는 것 (레퍼런스보다 우선)

디자인을 바꿔도 이 넷은 못 버린다. 우리 판정의 뜻이 여기 실려 있다.

| 규칙 | 왜 |
|---|---|
| **실선 = 확인함 / 점선 = 모른다** | 이걸 색으로만 하면 「모른다」가 「괜찮다」로 읽힌다 |
| **모든 수치 옆에 근거 링크**, 없으면 「주소 없음」 | 조용히 빼면 근거가 있는 척이 된다 |
| **판정은 「후보」로 표기** | 확정으로 보이면 실제 예산 삭감 근거로 오용된다 |
| **빈칸에는 이유를 적는다** | 「0건」만 있으면 도구가 고장난 줄 안다 |

색 세 개도 뜻이 정해져 있다 — 파랑 = 확인함, 붉은빛 = 비어 있음, 황토 = 모름.
**장식으로 쓰는 색은 없다.**

## 4. 스티치에 넣을 프롬프트 (초안)

> 스티치는 화면 하나씩 주는 편이 낫다. 아래를 페이지별로 나눠 넣는다.

### 공통 앞머리 (매번 붙인다)

```
한국 지방정부(인천광역시) 공무원이 쓰는 내부 검토 도구의 웹 화면.
장르는 대시보드가 아니라 "정부 사업을 위한 코드 리뷰 화면"에 가깝다.
검토 대상 사업 하나가 있고, 자동 점검 결과가 목록으로 나오고,
항목마다 원문 근거로 파고들 수 있다. 판정은 확정이 아니라 "후보"다.

톤: GitHub pull request의 Checks 화면 + Stripe 결제 상세 + Linear의 조밀함.
한국 정부 사이트의 촌스러움은 피하되 인쇄해서 결재에 붙일 수 있어야 한다.

색: 흰 배경(#ffffff), 페이지 바탕 연회색(#f4f5f7), 본문 먹색(#16191d),
    강조색은 파랑(#1f5fd0) 하나뿐. 경고는 벽돌빛(#c0392b), 보류는 황토(#8a6d1f).
    장식용 색·그라데이션·그림자 없음. 모서리는 6~8px로 절제.
글꼴: Pretendard. 제목 20~26px 700, 본문 13~14px, 캡션 12px. 숫자는 등폭.
선: 1px 실선 #e3e5e9. "확인함"은 실선, "아직 모름"은 점선으로 구분한다.
언어: 모든 문구는 한국어. 행정 용어 대신 쉬운 말.
```

### `/todo` — 지금 할 일 (가장 먼저 만들 화면)

```
[공통 앞머리]

화면 이름: 지금 할 일

상단: 검토 대상 사업 이름(20px 굵게)과 그 옆에 작은 "원문" 링크 뱃지.
      아래 한 줄에 산업·해주는 것·예산·협의처를 라벨/값 정의형 목록으로.

그 아래 요약 배너 한 줄: "손볼 것 4건 · 확인만 3건" (GitHub Checks 상단 배너처럼)

본문: 체크리스트 카드 목록 7개. 각 카드는
  - 왼쪽에 20px 정사각 번호 뱃지 (손볼 것은 벽돌빛 테두리, 확인만은 파랑 배경에 체크)
  - 제목 15px 굵게, 오른쪽에 "1건" 같은 작은 개수 뱃지
  - 그 아래 회색 한 줄: 지금 상태 ("사업 문서에는 A, 공식 예산 장부에는 B")
  - 그 아래 파란 한 줄: 하고 나면 ("엉뚱한 과로 공문이 가서 회신을 못 받는 일이 없습니다")
  - 오른쪽 끝에 "근거 보기 →" 링크

오른쪽 사이드(또는 아래): "이 산업에 무엇이 비었나"
  필요한 것 5가지를 가로 막대로. 채워진 칸은 파란 정사각형을 나란히,
  하나도 안 채워진 것은 벽돌빛 점선 빈 막대. 오른쪽에 "0÷2" 같은 비율.
```

### `/budget` — 예산이 제대로 붙어 있나

```
[공통 앞머리]

화면 이름: 예산이 제대로 붙어 있나

상단 지표 4개를 가로로: 장부와 일치 / 소관이 다름 / 금액 어긋남 / 못 찾음.
숫자는 22px 굵게, 라벨은 12px 회색. 카드 테두리는 1px 실선, 배경 흰색.

주 내용: "소관이 다릅니다" 표
  열 3개 — 사업 이름 / 사업 문서에 적힌 과 / 공식 예산 장부의 과
  사업 이름 옆에 작은 "원문" 링크 뱃지
  장부 쪽 값은 굵게, 그 아래 12px 회색으로 예산서 항목명
  경고 아이콘 없이, 왼쪽에 2px 벽돌빛 세로선만

아래: 대조가 끝난 사업 목록 (금액은 등폭 숫자, 오른쪽 정렬)

맨 아래 점선 테두리 박스:
  "아직 확인하지 못한 것 — 예산 장부 대조가 10건뿐입니다.
   '예산이 없다'는 뜻이 아닙니다."
```

### `/needs` — 필요한 걸 해주고 있나

```
[공통 앞머리]

화면 이름: 필요한 걸 해주고 있나

상단: 이 산업의 자료 상태 한 줄 — "이미 필요하다고 나옴" 또는 "아직 자료 없음" 뱃지와
      그렇게 본 이유 한 줄.

본문 위: 필요한 것 5~7가지 가로 막대 목록.
  왼쪽 4.5rem에 이름(사람/기술/돈/받쳐 줄 기업/공간·장비)과 그 아래 12px 설명,
  가운데 막대, 오른쪽에 "0÷2".
  비어 있는 줄은 이름을 벽돌빛으로, 막대를 점선 빈 칸으로.

비어 있는 항목 바로 아래 강조 박스 (Sentry의 원인 지목처럼):
  "여기서만 비어 있습니다. 「돈」을 해주는 사업은 다른 산업에 4건 있습니다
   — 로봇, 반도체."

그 아래 접히는 패널: "「돈」 자료는 어디서 찾나"
  출처 5줄. 각 줄은 [상태 뱃지] 기관 이름(링크) + 12px 설명.
  상태는 "지금 열림"(파랑) / "접속 막힘"(벽돌빛) / "청구해야 함"(황토 점선).
  맨 아래 회색 박스에 정보공개청구 문안 한 줄을 코드체로.

맨 아래: 자료 넣기 — 주소 붙여넣기 / 본문 붙여넣기 / PDF 올리기 탭 3개.
```

## 5. 스티치에 시키면 안 되는 것

- **판정 규칙을 바꾸는 문구** — 「중복 확정」 같은 말이 생기면 안 된다. 전부 「후보」
- **없는 지표를 만들어 넣기** — 스티치가 그럴듯한 차트를 채워 넣는다. 우리 데이터에
  없는 것은 화면에도 없어야 한다
- **다크 모드·그라데이션·일러스트**
- **영어 라벨** — 전부 한국어

받은 결과물은 **뼈대와 여백만 가져오고**, 문구와 숫자는 지금 API가 주는 것으로 교체한다.

| 무엇 | 어디 |

| Stripe 결제 상세 | stripe.com/docs 의 대시보드 이미지 |
| Sentry 이슈 상세 | sentry.io 제품 페이지 |
| 토스 | toss.im |
| KRDS | 한국 정부 디자인시스템 문서 |

> 실제 화면을 직접 보고 고르는 편이 낫다. 위 설명은 **무엇을 볼지 좁혀 주는 것**이지
> 화면을 대신하지 않는다.
